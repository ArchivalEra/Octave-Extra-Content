# 供给管线与经验（来自 Octave-Full-Wasm，2026-10-14）

> **性质**：操作手册。**本仓（Octave-Extra-Content）在管线里是"生产适配器"** ——
> 本文件讲的是：**本仓产出的东西靠什么被钉住、被核对、被消费**，以及那条管线上踩过的坑。
> **来源**：`Octave-Full-Wasm` 的实践（本仓即由它的 `shelf/` submodule 升格而来）。
> 所有"坑"都是**实测踩到**的，不是推测。

---

## §0 一句话

**管线 = 三件套 + 一条铁律**：
**身份（pin） + 字节（sha256） + 供给（provision） + 每提交的见证（witness）**；
铁律是 —— **"pin 的是 commit，用的是字节——两者必须被机器对账，人不能靠印象"**。

---

## §1 三件套：本仓占哪两件

| 件 | 是什么 | 本仓的载体 | 谁对账 |
|---|---|---|---|
| **① 身份** | "内容是什么、哪个版本" | **本仓 git 历史 + 宿主仓的 `shelf/` submodule pin** | 宿主 `witness-upstream-pin.py`（每提交） |
| **② 字节** | "字节是不是那份" | 每个版本的 **`sha256`**（包档案 / `recipes/*.md`） | `tools/forge-shelf.py --verify` + 宿主 `check_locks.py` |
| **③ 供给** | 把字节捞到站点（**宿主侧动作**） | 本仓只出**配方**（URL + sha256 + 预算） | 宿主 provision 脚本逐件核 sha |

**关键分工**：**本仓不含字节、不装配站点**。字节同源由**宿主**装配
（"同源"是 COEP 下的硬约束 —— 跨域 fetch 实测被拦，见宿主 `NOTES-client-compile-design.md` §1）。
本仓的角色 = **让"从哪取、取到的对不对"成为可复跑的事实**。

---

## §2 ★ sha256 要过三关（`fail-closed`，任何一关不符即拒）

```
① 采购关（本仓）    --fetch 取回 → 记 sha256 进档案 → --verify 复算
② 装配关（宿主）    forge-catalog.py 从本地缓存取 → 逐件核 sha → 装进站点
③ 客户端关（浏览器） assets-loader.js 在字节进包目录**之前**核 sha → 不符即拒、不写 FS
```

**为什么是三关而不是一关**：三处各有一个"我用的是哪份字节"的假设，
而**假设之间的漂移是无形的**（本仓实测形状：源码改了但装配产物没跟上 —— 见 §4 第 2 条）。
三关各配一条**反向断言**（篡改一个字节 ⇒ 必须拒），这是本仓纪律"断言要能证伪"的用法。

---

## §3 pin 的形态（三条路，各有其位）

| 内容类型 | 身份载体 | 例子 |
|---|---|---|
| 本仓自身 | **宿主仓的 submodule commit**（= 本仓某个 commit sha） | 宿主 pin `af7508c` |
| 包字节 | **per-version `sha256`**（档案里写死） | `optim-1.6.3` 的 sha |
| 无 git 的工具链/运行时 | **`URL + sha256`**（配方里写死） | LLVM-wasm bundle、Pyodide |

**⚠️ 一条硬纪律**：**URL 是"重取入口"，不是运行时依赖**。
即：配方里的 URL 只用来**取一次**（provision），此后一切核对靠 sha256；
上游把那个 URL 删了/换了，不影响已装配的站点，只影响"重取"。

## §4 ★ 实测踩过的坑（照抄会踩，逐条避开）

### 坑 1 · 仓里的东西 ≠ 装配产物里的东西（**"改了源≠装配跟上"**）
实测形状（2026-10-13：货架 submodule 已 pin 到 **12 包**，而站点装配产物停在 **10 包**；
宿主仓库镜像 `site/` 也停在 10 包）。⇒ **"我改好了"必须落到："装配产物真变了"** ——
判据 = 读**装配产物**再抽查装配结果，而不是读源码。
（本仓视角的推论：**加包之后要叫宿主重装配**，否则用户装不到。）

### 坑 2 · 同一个东西可能有"两份拷贝"，而你以为只有一份
- **容器里的构建树**是宿主仓 submodule 的**另一份拷贝**（改完仓里的脚本必须 `docker cp` 进去）；
- **本地缓存**（`third_party/forge/`）是"取包"的一次性产物，不随仓更新而更新；
- **站点字节**是装配产物，不是本仓内容。
⇒ 判据一律落到**正在被使用的那一份**上（读它的 sha / 读它的树）。

### 坑 3 · 白名单仓库：黑名单的漏看得见，白名单的漏**看不见**
本仓 `.gitignore` 是**白名单**（`*` + 逐条 `!路径`）。理由：
黑名单漏一条 = **忘了提交**（git status 看得见）；白名单漏一条 = **忘了报错**（文件根本不进 git，看不见）。
⇒ **新增文件/目录必须同步加一行 `!路径`**，且加完主动看一眼
`git status --short --ignored <新目录>`。

### 坑 4 · "上游发布件"不是持久制品
GitHub Release 资产**可以被删/被替换**。⇒ 配方写 URL + sha256 之后：
- 供给要**落持久盘备份**；
- 上游换件时，sha256 核对**必须红**（这正是 fail-closed 的用处）。
（同理：PyPI 的包会被 yank；本仓 `recipes/pyodide.md` 记录了一个真实的
"同一版本两个不同 sha"的身份坑 —— 那边是**上游自己重打包**造成的。）

### 坑 5 · `--selftest` 必须三档齐备（否则闸门会"空输入变绿"）
本仓工具的 17 条自证里显式含：**正常不报 / 该报的必须报 / 空输入必须报**。
实测过的假绿形状：站点同时缺文件 ⇒ parity 报"完全一致"；`declared == {}` ⇒ `verdict:"ok"`。
⇒ 每个新判据都要问："**输入消失时它会绿吗？**" 会 ⇒ 加零值守卫。

## §5 迁移/改名类操作的清点表（2026-10-14 实测有效）

本仓从 `Octave-Forge-Shelf` 迁到 `Octave-Extra-Content` 时用的流程，
**"换了地方但没换内容"这类操作照此做**：

```
① 推**完整历史**到新家（不是新建提交）⇒ 旧 commit sha 仍然可达
   ⇒ 宿主 submodule pin 的值**一个字都不用改**（只换 URL）
② 判"功能是否零差异"：git diff --quiet <旧pin> <新tip> -- <功能子树>
   实测：packages/ + tools/ 逐字节相同 ⇒ 判定"站点无需重装配"（8761 不动是底线）
③ 换 URL 的三处：.gitmodules（宿主）+ 子模块 remote + git submodule sync
④ 判"新家真能供出旧 pin"：git ls-remote 里能看到那个 sha 才算迁成功
⑤ 换完把**全部引用点**过一遍（宿主 grep 旧名），镜像/台账/文档一个不落
```

## §6 本仓"不做什么"（边界，写死）

- **不托管站点**、**不装配字节**、**不运行任何服务**（纯客户端铁律）；
- **不定义引擎接口**（引擎契约只能属于引擎）；
- **不改宿主仓**（路径铁律）；宿主的消费面由宿主维护。

> 分工的完整形状见宿主 `build/113/NOTES-extra-content-seam.md`（接缝）与其 §8（组织判决）。

## §7 复跑命令

```bash
# 字节核对（本仓）
python3 tools/forge-shelf.py --verify --cache /mnt/hdd/octave-wasm-build/third_party/forge
# 工具自证（三类用例齐备）
python3 tools/forge-shelf.py --selftest            # ⇒ 17 PASS / 0 fail
# 身份（本仓当前 tip —— pin 的候选值）
git rev-parse HEAD
# 配方里的 sha（抽一条）
sha256sum /mnt/hdd/zcode-projects/LLVM-wasm/release/llvm-wasm-bundle-v0.1.1.tar.gz
```
