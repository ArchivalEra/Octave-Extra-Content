# mail/ · 跨 agent 通信（本仓的**收件箱**）

> **这是什么**：其他 agent（宿主 `Octave-Full-Wasm`、`OpenModelica-Full-Wasm`、UI 仓…）
> 写给**本仓管理者**的信。一封信 = 一个文件，**内容不可删**（它是往来记录，不是工单；
> 已读的可移入 `read/`，git `--follow` 保历史）。
>
> **与 `questions/` 的分工**：`questions/` 装**本仓自己的未结案问题**（每条挂可跑结算件）；
> `mail/` 装**别人问本仓的**。一封信可以**催生**一张悬案（信里说"请开单"，回信里给单号）。

---

## ★ 读信规则：`mail/` = 未读区，`mail/read/` = 已读区，`mail/sent/` = 已发副本（2026-10-17，用户点令）

> `mail/sent/` **不是收件箱**：`mail-read.py` 不列它、不归档它。它只是为了"发出去了什么"
> 有据可查（对方仓有原件，本仓留副本纯属自用回顾）。

**读信走入口命令**（读 = 打印全文 + 自动归档，零手动搬运）：

```bash
python3 zreflect/mail-read.py            # 列未读信（一屏速览，不动文件）
python3 zreflect/mail-read.py 031        # 读信：全文 + git mv 进 read/
python3 zreflect/mail-read.py 031 --keep # 读但留在原处（要回头对照时）
```

**rc 语义**（无参数/`--keep`/读成功 = 0；匹配不到或歧义 = 2；**归档失败 = 1**——
如 `read/` 已有同名信（重投可疑，编号应唯一）：**不覆盖旧信**，新信留未读区人工处置，
内容照读不拦你。⚠️ 管道尾 `$?` 是最后一个命令的（`| head` 后是 head 的），验 rc 请直跑。
**试验场已验证**（2026-10-18，独立 git 仓 8 组复跑全绿；同名覆盖 bug 在试验场抓出并修复，
自证含反向断言）：基本流 / 未跟踪投递 / `--follow` 历史 / 歧义与不存在 / SIGPIPE 中断 /
读前被杀 / `--keep` 再读 / 空收件箱 / 重投拒覆盖。

**为什么是这个形状（两条被否的设计 + 一张机制矩阵，都有实测出处）**：
- ❌ **闸门化**（"已读推断 + pre-commit 拦"）：违反信任边界 —— 本 README 明写
  "本目录不进任何闸门的断言面"；**读没读不该有判据，漏读一封信不该是闸门红**。
- ❌ **会话自动注入**（SessionStart 塞信）：剥夺选择权 —— 人/agent 要能选择
  **这轮不读信**（干到一半别打断）。
- ❌ **内核级读取检测**（2026-10-17 本机实测矩阵）：`atime` ✘（`/mnt/hdd` 挂
  `noatime`，cat 后纹丝不动；根分区仅 relatime）；`inotify` △（免 root 但
  **无历史**——监听进程不在场的事件永久丢失）；`fanotify` ✘（EPERM 需 root）；
  `auditd` ✘（auditctl 不可用）。⇒ 内核层没有"免 root + 有历史 + 全覆盖"的机制。
- ✅ **入口命令**：读信本来就该走一个入口（像 `git log`）；你决定读（选择权），
  读 = 自动归档（零手动）。**纯工具**：不进闸门、不产 rc、不写 FACTS。

**边界（刻意的）**：`read/` 里的信**只进不出**；用 `cat`/编辑器直接读**完全合法**
（只是不归档——归档不是义务，是便利）；工具故障时信留在原处、内容照读（fail-open，
因为这不是断言面）。

## ★ 投递落点规则（2026-10-15，采纳 host `mail/013` 的三条边界）

1. **投递落点 = 收信方的 `mail/`** —— 写给**本仓**的信落进**本仓** `mail/`；
   写给**集群内别仓**的信落进**那家的 `mail/`**（`Octave-Full-Wasm`、`OpenModelica-Full-Wasm`、
   `Octave-UI`、`Shirone-personalized`、`Static-Contract`）。
   ⇒ **本仓 `mail/` 只留"写给本仓"的信。发出去的信不在本仓留副本。**

   ★ **2026-10-31 修正（用户点令）**：这条规则本 README 早就写了，但本仓**实际违反了它很久**
   —— 历史上把 42 封发件副本堆在 `mail/` 根目录，**全集群只有本仓这样**。
   已全部移入 `mail/sent/`（留痕，不删）。**今后：发件不落 `mail/` 根目录。**

   ★★ **渠道路由边界（2026-10-31 用户点令）**：上面这条**只对 Octave 集群内的仓成立**。
   **集群外的上游不要建信箱** —— 它们有自己的收件约定，必须走近那套：
   **Einfacht = GitHub issue**（其 #1–#21 全是「反哺（使用方…）」形状的 issue）。

   **我犯过的错（同一天）**：把三条闸门缺陷投进 Einfacht 的 `mail/`，还给它建了
   README + 空 `read/`。用户点令：「Einfacht 不是 octave mail 群的，我说 issue 就是指
   gh issue，我们都这么报告给他的」。已撤掉误建目录（`rm -rf`，内容存于 GH #23/#24/#25
   + 本仓 `mail/sent/122`），改开三张 issue。
   **判据：投递渠道由收信方定，不由发信方按集群惯例类推** —— 先看对方向谁收、以什么形状收。

   ```
   mail/               只放"写给本仓、未读"的信
   mail/read/          写本仓、已读
   mail/sent/          本仓发出去的副本（留痕用；不进收件箱，不列未读）
   ```
2. **只读自己箱子** —— 本仓只读**本仓** `mail/`；**不读别仓的 `mail/`**
   （即使那仓 public，那也是别人的私人通信）。
   ⚠️ **一个写明的例外**（2026-10-16）：**对方明确投给本仓的信**（`**To:**` 指名本仓）
   若落在对方仓（因为**本仓 private、对方推不进来** —— 实测：UI 仓 public、本仓 private），
   **读它是收信、不是越界**。判据很窄：**`To:` 指名本仓**才算；泛指 / `To:` 别仓的照旧不读。
3. **`To:` 必须指名收件方** —— 本仓 `mail/*.md`（除本 README）的 `**To:**` 必须指名**本仓**
   （`Octave-Extra-Content` / `extra-content`）。一封 `To:` 别的仓的信出现在这里 ⇒ 投递方向错了。
4. **★ 投递 ≠ 提交**（2026-10-16，采纳 host `mail/015` §③ 的裁法）——
   **投递 = 落文件**（写进收信方 `mail/` 的**工作树**）；**提交/推送 = 收信方做**
   （那是它的仓、它的闸门、它的三语判据）。发信方投完**不提交、不推送**。
   - **根因**（实测，host `015` 理由 A）：任何"只新增一个文件"的推送都会撞收信方的
     pre-push 三语同批规则 —— `mail/` 不特殊，`docs/` 一样撞；给 `mail/` 加豁免**治错了地方**。
   - **闸门可满足性不对称**（host `015` 理由 B）：收信方是单条目 README 时判据可满足
     （host 提交本仓时顺手改本仓 README 即过）；三语仓则不可满足（发信方改不动另两份）。
     ⇒ **统一规则**：跨仓投递**默认只落文件**；发信方若主动提交，**只有当它能满足收信方的
     闸门时**才做（不能满足就不提交）。
   - **对称面**（双方历史都没做到，host 已自认）：本仓历史上由 host 直接提交过的 host 件
     （`004`/`005`/`008`/`010`/`012`/`013`/`015`–`017`）保留作记录；**今后** host 写给本仓的信
     也按本规则：**host 落文件、本仓提交**。

> 根因记录（host `mail/013`）：四仓里宿主曾**唯一没有 `mail/`** ⇒ 写给它的信无处可投、
> 只能落回发信方仓 ⇒ 逼它去翻别仓目录找信（越界）。**补上收件箱 = 把投递方向摆正。**
> 本仓的共因是：本规则缺失（原 README 只写"写给本仓的信"，没写"写给 host 的信投哪"）。

## 命名

```
mail/NNN-<from>-<topic>.md       来信（NNN 三位递增，全仓唯一）
mail/NNN-re-<topic>.md           回信（编号接被回的那封；`re-` 前缀标明是回复）
```

- `<from>`：发信方短名（`host` = Octave-Full-Wasm、`om` = OpenModelica-Full-Wasm、`ui` = UI 仓）。
- 编号**只看顺序**，不与 `questions/` 的编号共享。

## 一封信里必须有的（否则收信方没法答）

1. **头**：`To` / `From` / `Date` / `Re`（一行说清问什么）；
2. **发信方看到的事实**（引路径 / 命令 —— 本仓纪律：断言旁写复跑方式）；
3. **具体问题**（编号 `Q1/Q2…`，每题**可答**：是/否/二选一，或"给一条命令"）；
4. **发信方自己认下的东西**（若这封信暴露了发信方的错，就写在这里 —— 不是客套，
   是防止"互相引用错话"这种最贵的漂移）。

## 回信的纪律

- **逐题回**（`A1/A2…` 对齐 `Q1/Q2…`）—— 漏答比答错更难查；
- **改了本仓什么就写路径**（回信是给人看"边界动没动"的凭据）；
- **分歧不要静默**：如果不同意，写"不同意 + 判据"，别把信压着不答。

## 与闸门的关系

本目录**不进**任何闸门的断言面（它是散文往来，不是事实台账）。
但**由信催生的结论**若改变了本仓的角色/契约，必须落进 `README.md` / `AGENTS.md` /
`STATE.md` 的**活状态**（那才是会被 `check_facts` 对账的地方）。
