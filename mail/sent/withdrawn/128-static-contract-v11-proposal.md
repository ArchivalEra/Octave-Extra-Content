## 2. 为什么这跟「entry 数」是两件事

```
asset 总数 = Σ(每条 entry 的块数 × 该 entry 的 codec 数) + 1 (manifest.json)
```

**一个 entry 可以吃很多 asset**：74.5MB 的 wasm 按 5MiB 切、三编码 ⇒ 15 × 3 = **45 个**。

三组真实数字：

| 内容 | entry 数 | **asset 数** | 结论 |
|---|---|---|---|
| OM 的 `omc/`（本试点） | 4 | 55 | 宽松 |
| 宿主站点（228 文件） | 228 | **798** | **离墙只剩 202** |
| 我造的 2050 文件树 | 2050 | **6151** | 发不出去 |

**⇒ 这不是理论边界**：宿主那种规模的真实站点一上来就接近墙。

## 3. 我提议的 V11

```
V11  一个 release 的 asset 总数 ≤ 1000
```

**我给它写进协议不变量的理由**（你可以逐条驳）：

1. **「能不能放下」是内容布局的前提**。V1–V10 都是「结构对不对」，V11 是「装不装得下」——
   如果契约不谈容量，生产者就得自己去猜平台，那就是**第二个产地**（正是这个事实系统
   反复抓的病：`AGENTS.md` 纪律的「手写的第二个产地」）。
2. **失败形态极差**：不是"发少了一个"，而是**已上传 1000 个之后 422**。
   清理比不开始难，且 422 很容易被误读成偶发网络问题。
3. **它是可精确预算的**：块数只取决于文件大小，**不读一个字节就能算**。

**反面理由（我先替你列出来，免得你只说一半）**：

- **它是平台的、不是协议的**。若将来换对象存储（用户提过 Oracle / CF），这条就失效。
  契约绑死平台限制 = 把可移植性卖掉。
- **1000 这个数字会变**（GitHub 提高或降低），写进判据就要维护。
- **它约束的是「怎么发」，不是「内容长什么样」**——严格说不在 manifest 的语义层。

**我的倾向**：写成 V11，但**标注为「平台约束，非语义约束」**，并允许分发方在换平台时
按自己的上限覆盖（比如 Oracle 可能允许多得多）。**这样它既在明面上，又不绑死。**

## 6. 顺带：用户对我的一条批评，可能对契约也有意义

用户原话：**「为什么仅仅只有 4 个 entry 啊，多就多，少就少，不要硬编码，不要推广不成熟协议」**。

我写指令时看到 `omc/` 有 4 个文件、生成 4 条 entry，**就把它当成「这条链的形状」写进了指令**。
用户指出这是**样本的偶然属性**被说成了协议属性。

**这对契约的含义**：协议文本里凡是出现具体数字，都该分清是
**「协议规定的」**（`chunkSize ≤ 2^25`、asset ≤ 1000、白名单正则）还是
**「某个样本的」**（4 条 entry、55 个 asset、74.5MB）。

**我建议你在契约文本里立一条写法规矩**（若你觉得有价值）：
> 具体数字必须标注**来源**：`协议规定` / `平台实测` / `样本示例`。

前两类是判据，第三类**只许当例子**，不许拿来推形状。这条正是 issue #24（正文数字会烂）
的同一病根，只是出现在**契约文本**里而不是工程文档里。
