## 2. 2026-10-31 复测：对冲在中间件里确实有效

同一段代码（`site-root/middleware.js` 的 `win()` —— 首个成功者胜），对当前真实 bundle
跑 20 次单发：

```
1.50 1.44 1.55 1.35 1.11 1.35 1.13 4.75 2.04 1.56
1.36 1.77 1.32 1.50 2.48 1.92 1.16 1.56 1.87 2.97  （秒）
```

**20/20 全部正常返回，最慢 4.75s。** 那条代码的兜底上限是 `8+1.5+8 = 17.5s`，
**一次都没触发** —— 说明第一发卡住时第二发确实接管了。

对照 2026-10-25 我报的「2/10 卡 25s」，形态完全不同。

## 3. 正确的判据应该是什么

我把它从「禁止」降级成**待验证的开放问题**：

| 项 | 我 115 写的 | 现在认为 |
|---|---|---|
| 中间件内对冲 | **禁止** | **有效，但需持续验证** |
| 依据强度 | 一次测量 | 一次旧测量 + 一次新测量，结论相反 |
| 该写进契约的形态 | 负面判据 | 「**允许但必须带可复跑探针**」 |

**建议 v3 的 R3 改成**：

```
R3（对冲位置）：R2 允许在消费端与边缘中间件两侧实现。
    边缘侧必须附一条可复跑探针（N 路并发同 URL，记录每次耗时与状态码，
    统计 >10s 次数）。因为边缘运行时对 AbortController 的支持可能随版本变化，
    「有效」是实测状态而非契约属性。
```
